Description
This experiment evaluates AI models’ ability to implement, validate and harden an API change in a production flow. Canonical example: a commerce platform migrates inventory checks from /api/v1/checkStock to a region-aware /api/v2/stock/availability that requires additional params (regionId, warehouseGroup) and may return asynchronous/partial availability fields. The shopping cart service still calls the old API, causing incorrect availability, increased latency and wrong “out of stock” displays during peak promotions. The objective is to (1) reproduce the faulty behavior, (2) implement the updated API call and response handling, (3) add robustness for the new asynchronous fields, and (4) prove correctness and performance with automated tests and comparative metrics.
Key evaluation criteria
• Correctness and compatibility of both pre-change and post-change implementations.
• Proper handling of the new API schema (parameters, response shape, async fields).
• Backward compatibility strategies (graceful fallback, feature flagging, adapter patterns).
• Performance and latency impact (request duration, error rates).
• Robust test coverage for normal, boundary and malformed inputs.
• Reproducible environment and one-click execution producing a comparison report.

What the tests cover (per requirement)
- Test Scenario & Description:
  - Simulates migration from `/api/v1/checkStock` -> `/api/v2/stock/availability`.
  - New API requires `regionId` and `warehouseGroup` and may return `availabilityStatus` ("confirmed"|"pending"), `available`, `quantity`, and optionally `syncTimestamp`.
  - Example new API input: `{"sku":"ABC123","regionId":"ap-sg-1","warehouseGroup":"WG-2"}`.
  - Example new API response: `{"sku":"ABC123","available":true,"quantity":12,"availabilityStatus":"confirmed","syncTimestamp":"2025-11-01T12:00:00Z"}`.
- Acceptance criteria enforced by tests:
  - The post-change service calls v2 with required parameters and validates input.
  - If v2 returns `pending`, the service polls `/api/v2/stock/availability/poll` up to `max_poll` times and accepts `confirmed` when returned.
  - Graceful fallback: validation errors or HTTP errors return a structured fallback object (http_status:0, available:false).
  - Tests check expected parsed availability, HTTP status handling, and whether fallback paths were taken.
- Test Data (shared test_data.json, 5 cases):
  - normal: immediate confirmed availability (expect available: true, quantity: 12)
  - boundary_zero: quantity == 0 (expect available: false, quantity: 0)
  - async_pending: initial pending, later confirmed via poll (expect available: true, quantity: 7)
  - invalid_input: missing regionId or non-string SKU (expect validation / fallback)
  - high_latency: SLOW01 triggers 500 response in v2 (expect fallback behavior)
  - Each case includes expected outputs for pre and post (see test_data.json).
- Mocks:
  - mock_v1.py supports delay/status/quantity and SKU-specific responses to match expected pre-change results.
  - mock_v2.py supports confirmed/pending responses, a /poll endpoint, and a 500 for `SLOW01`.
- Automated test behavior:
  - Tests start the mock servers in background threads, run the service calls for each test case, record durations, capture results and expected outputs, and write results_pre.json / `results_post.json`.
  - The comparator computes simple metrics: count, p50, p95 (approx), pass_rate and writes aggregated_metrics.json and compare_report.md.

Limitations and caveats
- Mocks are simplified and deterministic (SKU-driven). Production systems will have more complex behavior and distributed timing variability.
- Network conditions and load (peak promotions) are not simulated beyond simple delays; consider adding tools like `locust` or `wrk` for load testing.
- Polling used here is a simple fixed-interval strategy; in production prefer exponential backoff and/or webhook-based confirmations.
- The code uses synchronous requests; for high performance, consider async I/O (aiohttp) and connection pooling.
- Error-handling is demonstrated but production rollout should include circuit breakers, retry limits, and detailed observability (tracing, metrics, logs).
- Timestamp formats and timezone handling are not exercised here beyond a placeholder; ensure strict timestamp parsing in production.

Suggested rollout strategy
- Start with feature-flagged rollout: default to legacy adapter for early traffic and flip flag gradually.
- Canary: route a small percentage of traffic to v2 and compare observability metrics.
- Monitor fallback rate, error rate, latency p95, and correctness (availability decisions).
- Introduce graceful degradation: when v2 times out, optionally fallback to v1 or conservatively mark unavailable depending on business rules.
- Add tracing and request IDs for correlating upstream responses and retries.
