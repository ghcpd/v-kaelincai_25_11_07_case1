Scenario:
- Legacy API: POST /api/v1/checkStock — input: {"sku":"ABC123"} returns {"sku": "ABC123", "available": true, "quantity": 12}
- New API: POST /api/v2/stock/availability — input: {"sku":"ABC123","regionId":"ap-sg-1","warehouseGroup":"WG-2"} returns:
  - Immediate confirm: {"sku":"ABC123","available":true,"quantity":12,"availabilityStatus":"confirmed"}
  - Async pending: {"sku":"ASYNC1","availabilityStatus":"pending","syncTimestamp":"2025-11-01T12:00:00Z"}
  - Error/latency: HTTP 500, or timeout

Acceptance Criteria:
- Pre-change service uses /api/v1.
- Post-change service calls /api/v2 with the new params.
- Post-change service polls on "pending" and falls back to v1 if unresolved or if v2 errors.
- Tests verify that post migration produces identical or improved behavior (availability correctness) or degrades gracefully.

## 🔧 How the Service Changes Work

- In Project_A, `cart_service_v1` uses the legacy v1 endpoint only (SKU only).
- In Project_B, `cart_service_v2`:
  - Sends v2 payload: sku + regionId + warehouseGroup.
  - Checks `availabilityStatus`.
    - If `confirmed`, returns the v2 result.
    - If `pending`, polls at `POLL_INTERVAL` until `POLL_TIMEOUT`.
    - If still pending or error or invalid response, falls back to v1 and returns v1 result.
  - Returns `meta` with `{ duration: <seconds>, fallback: <true|false> }`.

This qualifies as an adapter approach that preserves backward compatibility and adds region-awareness and async handling.

## ⚠️ Limitations & Known Issues

- Mocks are deterministic and simulate errors/latency via sleep; they do not emulate all real-world network conditions.
- The polling strategy is implemented using simple intervals & timeouts; production may prefer webhooks or event-driven updates.
- Real production systems should:
  - Add robust observability: trace ids, metrics, logs, and dashboards for pending responses and fallback frequency
  - Add circuit-breakers and backoff on the v2 calls
  - Add validation and schema parsing (e.g., using Pydantic or JSON schema)
  - Perform a canary and staged rollout (region-based toggles)
