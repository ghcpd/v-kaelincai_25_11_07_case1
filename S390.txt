• Proper handling of the new API schema (parameters, response shape, async fields).
• Backward compatibility strategies (graceful fallback, feature flagging, adapter patterns).
• Performance and latency impact (request duration, error rates).
• Robust test coverage for normal, boundary and malformed inputs.
• Reproducible environment and one-click execution producing a comparison report.

## Acceptance Criteria Implemented
- The "pre-change" project uses legacy endpoint; tests validate legacy correctness (baseline).
- The "post-change" project:
  - Calls v2 with required params (`regionId`, `warehouseGroup`).
  - Correctly handles `availabilityStatus == "confirmed"`.
  - On `pending`, it polls the v2 endpoint until `confirmed` (or until a timeout), then returns the final result.
  - On timeout, unknown statuses, or exceptions, it gracefully falls back to the v1 endpoint (adapter pattern).
  - Returns code `400` when required v2 parameters are missing (client validation), and does not fallback for parameter error.
- Tests automatically validate results vs test expectations, capture durations, and flag fallback occurrences.

## Pitfalls and mitigations (README highlights)
- Schema drift:
  - Mitigation: validate response shapes and required fields; strong typing/strict serializers.
- Async (eventual) consistency:
  - Mitigation: implement polling with timeouts, retriable idempotent operations, minimal backoff, and instrumentation.
- Failure modes and cascading failure:
  - Mitigation: implement circuit breakers & fallback path to v1; ensure fallbacks are recorded and throttled.
- Timestamps & timezone handling:
  - Mitigation: use canonical RFC 3339 / ISO8601 with explicit timezone; robust parsing; avoid ambiguous naive datetimes.
- Mock fidelity:
  - Tests use mocks but real-world integrations should run canary and progressive rollouts.

---

## Limitations of this repo
- Mocks emulate the API but lack production-level simulations (auth, load balancing, true network variability).
- Polling is simplistic; production should use backoff strategies and opt for webhooks/notifications where possible.
- All scripts use a small polling window and timeouts for speed during tests.
