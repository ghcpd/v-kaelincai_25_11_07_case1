## 🎯 Test Scenario & Acceptance Criteria (key points)
- Scenario: Migrate from /api/v1/checkStock → /api/v2/stock/availability adding regionId & warehouseGroup and possibly returning `availabilityStatus` {confirmed, pending} and `syncTimestamp` for async updates.
- Input format (v2): {"sku":"ABC123","regionId":"ap-sg-1","warehouseGroup":"WG-2","quantity":1}
- Example v2 response:
  - Immediate: {"sku":"ABC123","available":true,"quantity":12,"availabilityStatus":"confirmed","syncTimestamp":"2025-11-01T12:00:00Z"}
  - Async/partial: {"availabilityStatus":"pending","syncTimestamp":"2025-11-01T12:03:00Z"}
- Acceptance:
  - Service uses v2 when USE_V2 enabled and sends new required params
  - Properly interprets async responses via polling with bounded retries
  - Graceful fallback to legacy v1 if missing v2 params, v2 timeouts or errors
  - Behavior is compatible or improves user-facing decisions (out-of-stock detection accuracy)
  - Tests validate correctness and capture timing and fallback frequency

## 🧩 Implementation details & robustness
- Adapter pattern: `cart_service_v2.check_stock` decides to call v2 or fall back to `call_v1`. A feature flag `USE_V2` toggles v2 for staged rollout.
- Async fields: For v2 `availabilityStatus: "pending"`, `call_v2` performs limited polling (configurable attempts + backoff). On repeated pending state it returns a partial decision and the system falls back optionally.
- Fallback: fallback to v1 when v2 fails or returns invalid schema. This minimizes user-facing breakage during rollout.
- Observability: tests capture durations per request and a `fallback` boolean. The compare tool computes p50/p95 and fallback frequency.

## ⚠️ Important notes / limitations
- Mocks are simplified; real production systems may need webhook callbacks or event-driven updates for asynchronous availability.
- Network conditions (packet loss, large-scale concurrency) and long tail latencies require more realistic load testing; these scripts simulate latency but do not fully emulate production load.
- Polling is simple; production should implement exponential backoff and idempotent request semantics, and prefer webhooks when possible.

## 📄 Suggested rollout recommendations
- Add a feature flag and test with canary traffic to reduce blast radius.
- Monitor fallback frequency, error rate, and P95 latency — these metrics determine if v2 is stable for full rollout.
- Add schema validation and strict logging of mismatch fields to avoid silent errors during upgrade.
- Use circuit breaker patterns if v2 fails repeatedly.
